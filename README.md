# Proton Mail Playwright Automation Assessment

## Overview

This project contains a focused end-to-end UI automation suite for Proton Mail Web using Playwright and JavaScript.

The suite contains 19 high-value scenarios across authentication, compose/send, drafts, inbox actions, folders/labels, search, filters, asynchronous workflows, and attachments.

The framework uses the Page Object Model, Playwright Test, reusable application actions, explicit state assertions, authentication state reuse, and parallel execution where tests are independent.

### ⚠️ Security note

`.env` **must** be in `.gitignore`. If it is ever committed (checked with `git log --all --full-history -- .env`), treat the credentials inside it as compromised: rotate the Proton account passwords immediately and remove the file from git history (`git rm --cached .env`, commit, then rewrite history with a tool such as `git filter-repo` before treating the repository as clean), not just delete it from the latest commit.

## Authentication

Authentication is performed by `tests/auth.setup.js`.

The setup:
1. Logs into Proton Mail.
2. Verifies the authenticated state.
3. Saves the browser storage state to `.auth/sender.json`.

The main test project reuses that state through Playwright `storageState`.

This avoids repeating the login UI flow for every authenticated test.

If the stored session expires, rerun the setup/authentication flow to regenerate the state.

> **Note:** confirm which account credentials `auth.setup.js` logs in with before relying on `.auth/sender.json` — the file name implies the sender account, and downstream tests are written against that assumption.

## Execution Strategy

The suite uses Playwright workers so independent test files can execute in parallel.

Where ordering is intentionally required inside a file, tests are configured as serial (used in `tests/inbox.spec.js`, since star/archive/delete-restore act on the same message list):

```javascript
test.describe.configure({ mode: 'serial' });
```

This gives a structure such as:

```text
Worker 1 -> inbox.spec.js
            INBOX-001 -> INBOX-002 -> INBOX-003 -> INBOX-004

Worker 2 -> search.spec.js
            SEARCH-001 -> SEARCH-002

Worker 3 -> attachments.spec.js
            ATTACH-001 -> ATTACH-002
```

Serial mode controls scheduling/order; it does not automatically share browser state between tests.

Unique test subjects/data are used where appropriate to reduce collisions.

## Synchronization

The suite relies on Playwright auto-waiting and explicit state assertions.

Examples:

```javascript
await expect(locator).toBeVisible();
```

Hard-coded sleeps (`page.waitForTimeout`) are not used anywhere in the suite.

For asynchronous workflows, the test waits for observable UI state rather than relying on arbitrary delays.

## Test Data and Assumptions

- Two dedicated Proton Mail test accounts are used (`SENDER_EMAIL`/`SENDER_PASSWORD` and `RECEIVER_EMAIL`/`RECEIVER_PASSWORD`), enabling a real sender → receiver mail flow.
- Credentials are supplied externally via `.env` (never committed — see the Security note above).
- Repeatable message content lives in `test-data/mailData.json`; `test-data/sample.txt` is used as the attachment fixture for ATTACH-001/ATTACH-002.
- Test data may remain in the mailbox unless cleanup is implemented.
- Unique subjects are preferred when tests can run in parallel.
- Mail delivery and some asynchronous workflows can depend on external system behavior.
- The UI may change over time, requiring locator maintenance.

## Defects and Findings

The assessment asks for genuine defects and explicitly says not to manufacture bugs.

No Proton Mail product defect is claimed in this submission unless it was reproduced and supported by evidence.

Two automation/environment findings are documented in `DEFECT_REPORT.md`:
- An authentication/session-expiry observation encountered during development.
- A possible naming/account mismatch in `auth.setup.js` (logs in as `RECEIVER_EMAIL` but stores the session as `.auth/sender.json`), flagged for verification rather than asserted as confirmed.

## What Was Deliberately Not Automated

- Exhaustive visual/UI consistency testing.
- Broad accessibility testing requiring human assessment.
- CAPTCHA/MFA flows requiring special account configuration or human interaction.
- Exhaustive browser/device combinations.
- Long-running scheduled delivery verification.
- Exploratory security/privacy testing requiring threat-model-driven investigation.

These remain valuable areas, but are outside the focused regression scope.

## Automation Quality Review

### 1. Which tests were deliberately not automated, and why?

I prioritized stable, repeatable, high-value regression workflows. Visual review, broad accessibility exploration, CAPTCHA/MFA, exhaustive browser/device coverage, and long-running scheduled delivery are better handled through targeted manual/exploratory testing or separate specialized suites.

### 2. Which 5 tests would run on every pull request?

I would select:

1. AUTH-001 — Valid login
2. MAIL-001 — Valid send
3. DRAFT-001 — Draft auto-save
4. INBOX-002 — Star/unstar
5. SEARCH-001 — Keyword/sender search

These cover authentication, the primary send journey, persistence, a common message action, and retrieval. The remaining regression suite can run on a broader schedule (nightly) when execution time becomes significant — the full 19-scenario run currently completes in roughly 7 minutes across categories, so nightly is a comfortable cadence as the suite grows.

### 3. How would I diagnose a test that passes locally but fails intermittently in CI?

I would first compare browser, OS, Node/Playwright versions and configuration. Then inspect the Playwright trace, screenshot, video/logs, timing, network failures, console errors, and authentication state. I would identify whether the cause is synchronization, environment latency, test-data collision, session expiry, or an actual product defect before changing the test.

### 4. How would I reduce flakiness if the UI changes frequently?

Use stable user-facing locators and `data-testid` attributes where available, centralize selectors in Page Objects, avoid long generated XPath/CSS paths, use state-based synchronization, and keep assertions focused on business outcomes. I would also reduce duplicated locator logic so UI changes are fixed in one place. (Current page objects mix `getByRole`/`getByText` with some XPath even for `data-testid` lookups — e.g. `//*[contains(@data-testid,"composer:close-button")]` in `ComposePage.js` — those could be simplified to `page.getByTestId(...)` for consistency with the stated locator strategy.)

### 5. How would I scale from 20 to 200+ tests?

I would introduce reusable component objects and fixtures, centralized test-data builders, authentication fixtures for different roles, suite tagging, smoke/regression separation, API/direct-data setup where safe, and stronger test isolation. The goal would be to keep business workflows readable while preventing duplicated UI implementation details.

## Troubleshooting

### Authentication/session expired

Regenerate the authentication state by running the setup/authentication flow. Do not commit `.auth/sender.json`.

### Test fails due to stale mailbox data

Use a dedicated test account and unique subjects/test data. Clean up test-created messages where practical.

### Locator failure

Run headed mode:

```bash
npx playwright test --headed
```

Then inspect the Playwright trace/report and confirm the application state before changing the locator.
